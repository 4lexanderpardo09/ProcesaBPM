# ProcesaBPM: arquitectura y organización de carpetas

> Estado: **propuesta vigente** (2026-09-30). Aplica a todo el código nuevo. Si una decisión cambia, se actualiza aquí.
> Reglas de código (inglés, tests, clean code): `CLAUDE.md`. Capa de datos: `base-de-datos.md`.

## 1. Monorepo
```
ProcesaBPM/
├── apps/
│   ├── api/              # 🚧 NestJS: API HTTP + worker. Hecho: config, database (tenant), common (errores, logger, health). Faltan los módulos de §3.1
│   └── web/              # React + Vite: la aplicación del cliente
├── packages/
│   ├── db/               # ✅ hecho: Prisma, migraciones, semilla, pruebas de BD
│   └── shared/           # 🚧 en curso: lógica de dominio pura (engine/business-time, conditions, formulas, wait, fields, routing; calculators; workflow; contracts; errors)
├── docs/                 # documentación (español)
├── scripts/              # cloud-setup.sh y utilidades
├── docker-compose.yml    # desarrollo: postgres 18, seaweedfs (S3), redis, mailpit
└── pnpm-workspace.yaml
```
**Dependencias permitidas:** `web → shared`; `api → shared, db`; `shared → (nada del proyecto)`; `db → (nada del proyecto)`. El front **nunca** importa `db` ni `api`.

## 2. `packages/shared`: el contrato y la lógica pura
```
packages/shared/src/
├── contracts/            # esquemas zod de requests/responses por dominio (tickets, workflows, …)
├── workflow/             # esquemas de config por tipo de bloque, validador del grafo antes de publicar
├── engine/               # lógica pura del motor, sin I/O:
│   ├── business-time/    #   cálculo de vencimiento y minutos hábiles (calendario, franjas, festivos, zona)
│   ├── conditions/       #   evaluador de condiciones (igual, distinto, empieza_con, contiene, en_lista, >, <, fechas)
│   ├── formulas/         #   ✅ lenguaje de fórmulas (analizador, tipos, evaluador, orden de dependencias)
│   ├── money/            #   ✅ Decimal exacto (escala 10^12)
│   ├── wait/             #   ✅ cuándo despierta un bloque WAIT
│   └── fields/           #   ✅ validación de valores, totales de tablas
├── calculators/          # ✅ calculadoras integradas (MEAL_ALLOWANCE); el saldo de viáticos es una fórmula
├── permissions/          # acciones y sujetos CASL (tipos compartidos)
└── errors/               # ✅ errores de dominio tipados y mapeo de SQLSTATE de la BD (23001, 23514, 23503, 23505, 23P01, 42501)
```
Todo lo que se calcula en ambos lados (el SLA que ve el usuario, las fórmulas del formulario) vive **una sola vez** aquí. Así se evita lo que pasaba en el sistema viejo con `table-field.util.ts` ↔ `tableField.ts`, duplicados a mano. Pruebas: solo unitarias (`*.spec.ts`), con tablas de casos.

## 3. `apps/api`: NestJS por dominios, en capas
```
apps/api/
├── src/
│   ├── main.ts                  # entrada HTTP
│   ├── worker.ts                # entrada del worker (colas, crons, outbox)
│   ├── app.module.ts
│   ├── config/                  # variables de entorno validadas con zod (no arranca si falta una)
│   ├── common/                  # transversal: guards (JWT, políticas CASL deny-by-default),
│   │                            #   filtro de errores (mapea SQLSTATE → HTTP), paginación, logger con tenant_id
│   ├── infrastructure/          # adaptadores técnicos, sin reglas de negocio
│   │   ├── database/            #   PrismaService + extensión de contexto de tenant + helper de transacción
│   │   ├── storage/             #   StorageProvider S3-compatible (SeaweedFS/R2)
│   │   ├── queue/               #   BullMQ + outbox dispatcher
│   │   ├── mail/                #   proveedor de correo
│   │   ├── crypto/              #   AES-256-GCM (secretos de webhooks y MFA)
│   │   └── realtime/            #   gateway Socket.IO con adaptador Redis
│   └── modules/                 # un módulo por dominio (ver lista abajo)
└── test/
    ├── integration/             # repositorios y casos de uso contra PostgreSQL real
    └── e2e/                     # HTTP de punta a punta (supertest) + test de fuga entre tenants
```

### 3.1 Módulos
| Módulo | Responsabilidad |
|---|---|
| `auth` | Login, selector de organización, JWT + refresh, recuperación, MFA, invitaciones. |
| `platform` | Alta de tenants (roles base, calendario, empresa por defecto), planes, suspensión y purga. Usa el login de plataforma. |
| `authorization` | Habilidad CASL por miembro, decoradores de permisos, guard global y acceso por registro (§9). |
| `identity` | Miembros, roles, permisos, grupos. |
| `organization` | Empresas, departamentos, cargos, sedes, calendarios. |
| `approvals` | Grupos de aprobación, delegaciones y **resolución del aprobador** (§8.12 de base-de-datos.md). |
| `catalog` | Categorías, subcategorías, prioridades. `GET /catalog/available` solo ofrece lo que la persona puede iniciar de verdad (2026-10-09): además de la visibilidad por empresa y departamento, deja fuera las subcategorías sin versión publicada y ejecutable y aquellas cuyos bloques START no la admiten (iniciadores) para ninguna de las empresas consultadas. Usa `CreationGate` del motor (las mismas reglas que crear el ticket) y una sola consulta de versiones para todas las subcategorías (los documentos salen de la caché de `PublishedVersionReader`). No aplica las condiciones guardadas en el permiso `create`: esas se comprueban al pedir el formulario y al crear. |
| `workflows` | Constructor: versiones, bloques, transiciones, campos, topes, validación y publicación. |
| `engine` | **Hecho (núcleo):** iniciar, avanzar, reasignar, tomar de un pool y cerrar; resolver responsables; recorrer los bloques automáticos; topes de monto (§14). |
| `tickets` | **Hecho:** `GET /tickets`, detalle con autorización por registro, línea de tiempo y las rutas de `engine` (§14): crear, avanzar, reasignar, tomar, comentar, cerrar, reabrir, novedades y tareas paralelas. Las etiquetas van en `tags`; los tipos de error, en el catálogo. **Formularios para la web:** `GET /subcategories/:id/creation-form?companyId=` (crear para uno mismo: los bloques START que lo admiten, con sus campos de creación en orden; mismas comprobaciones y errores que crear: subcategoría disponible, versión publicada y ejecutable, permiso `create` sobre ese registro e iniciadores, extraídas a `engine/application/creation-gate.ts` para que el formulario nunca ofrezca lo que la creación rechazaría) y `GET /tickets/:id/form` (quien puede leer el ticket: el paso actual, todos los campos de la versión para mostrar los valores, los que se llenan en ese paso y las decisiones en orden; `step: null` al cerrarse). Ver el formulario no da permiso para actuar: avanzar sigue pasando por el motor. |
| `tags` | **Hecho:** etiquetas personales del miembro (`tags`) y las que pone en un ticket (`ticket_tags`): `GET/POST/PATCH/DELETE /tags` y `GET/POST/DELETE /tickets/:id/tags`. Una etiqueta es de su dueño y solo él la ve; para ponerla en un ticket hay que poder leerlo (autorización por registro). El listado y el detalle del ticket traen las etiquetas del que consulta. |
| `text-templates` | **Hecho:** plantillas de texto personales (`text_templates`) y sus comparticiones de solo lectura (`text_template_shares`): `GET/POST/PATCH/DELETE /text-templates`, `GET/PUT /text-templates/:id/shares`. Solo el dueño edita y comparte; un compartido se lee pero no se toca. Solo se comparte con miembros `ACTIVE`: un invitado, un inactivo o alguien de fuera se descarta sin decir quién es. El HTML se sanea al guardar. |
| `sla` | **Hecho:** cálculo puro de vencimiento y cierre (`domain/clock-math.ts`), de pausas por novedad (`domain/pause-math.ts`) y el job del worker que avisa relojes vencidos. |
| `notifications` | **Hecho:** avisos en la app y por correo de los eventos de tickets (a quién: `domain/recipient-policy.ts`; solo a quien puede leer el ticket), preferencias por tipo y los endpoints de «mis notificaciones». Módulo del worker (`notifications-worker.module.ts`) y módulo del API (`notifications.module.ts`). Detalle en base-de-datos.md §8.17. |
| `files` | **Hecho:** subida en dos fases (reservar con cuota → confirmar por primeros bytes), cuota por plan con gracia, adjuntos de tickets y campos `FILE`, descargas firmadas, purge de subidas abandonadas en el worker (§8.14 de base-de-datos.md). El puerto `ObjectStorage` y sus adaptadores (S3/MinIO e in-memory) viven en `infrastructure/storage`; las reglas puras de tipos y el sniffer en `packages/shared/src/files`. |
| `documents` | Formatos PDF, plantillas (coordenadas/AcroForm) y generación versionada. |
| `exports` | Exportaciones programadas (planos). |
| `data-exports` | **Hecho:** exportación de los datos de la organización durante el periodo de eliminación: solicitudes, estado y enlaces de descarga en el API (parte 1) y el worker que arma el zip y avisa por correo (parte 2, `data-exports-worker.module.ts`) (§20). |
| `notifications` | In-app, correo, tiempo real y preferencias. |
| `webhooks` | Suscripciones y entregas firmadas. |
| `datasets` | **Hecho:** Excel como fuente de valores de los campos (el `tm_data_excel` de la mesa de ayuda). Administración con los permisos de flujos (`read`/`update Workflow`): `GET/POST /datasets`, `GET/PATCH/DELETE /datasets/:id`, `GET /datasets/:id/rows` y `PUT /datasets/:id/content` (recargar). El `.xlsx` se sube con la subida en dos fases y se apunta por `fileId`; se lee la primera hoja, con la primera fila como encabezados (hasta 50 columnas y 20 000 filas, celdas de hasta 1 000 caracteres) y **todo valor se guarda como texto** (un número `1234567890` coincide con lo que escribe el formulario; una fecha sin hora queda `YYYY-MM-DD`). Columna clave opcional (`keyColumn`, sin repetidos ni vacíos) guardada en `lookup_key`, y marcada en `columns` (`[{name, isKey}]`, sin migración). Antes de leer, el zip se recorre con yauzl contando lo que de verdad infla (tope 64 MB y 2 000 entradas): una bomba zip se rechaza sin cargarla en memoria. El archivo y la verificación corren sin transacción abierta; luego todo se escribe de una vez (un archivo rechazado no deja nada). No se puede borrar si algún campo lo usa (en cualquier versión: hay que desactivarlo) y una recarga no puede quitar una columna que un campo lee ni la clave si un campo busca por ella (409 `DATASET_IN_USE` con las columnas). Para quien llena el formulario (`create`, `create_for_others` o `transition` de `Ticket`): `GET /fields/:fieldId/dataset-options?q=` (valores distintos de la columna del campo que contienen el texto, sin distinguir mayúsculas) y `GET /fields/:fieldId/dataset-lookup?key=` (el valor de la columna del campo en la fila con esa clave, para `lookupFieldCode`). Siempre se pregunta por un campo de una versión no borrador y solo vuelve su columna, nunca la fila completa. |
| `dashboard` | **Hecho:** el resumen del propio miembro: `GET /dashboard/stats` (asignados abiertos o pausados, vencidos, por vencer en 24 h, creados abiertos y cerrados en 7 días) y `GET /dashboard/pending` (sus tickets en curso, hasta 100, lo más urgente primero: el orden por vencimiento se decide en la BD antes del límite y el resto va después). Todo acotado a lo que puede leer (`read Ticket`, autorización por registro). |
| `reports` | Indicadores y exportes. |
| `audit` | Registro y consulta de auditoría. |
| `retention` | **Hecho (solo el worker):** borrado nocturno de lo que pasó su ventana de retención (§17 y base-de-datos.md §8.27). |

### 3.2 Forma interna de cada módulo
```
modules/tickets/
├── tickets.module.ts
├── http/                    # controllers + mapeo DTO ↔ caso de uso (sin lógica de negocio)
├── application/             # casos de uso / servicios: create-ticket.service.ts, close-ticket.service.ts…
├── domain/                  # reglas puras: entidades, value objects, errores tipados (sin Nest ni Prisma)
├── data/                    # repositorios Prisma (única capa que toca la BD)
└── *.spec.ts                # unit tests junto al archivo que prueban
```
Reglas:
- **Flujo:** `http → application → domain`, y `application → data`.
- **Un módulo no importa los repositorios de otro:** usa su servicio público o un evento de dominio.
- **Efectos externos** (PDF, correo, websocket, webhooks) salen por el outbox, nunca dentro de la transacción.
- **Los controllers solo declaran:** ruta, validación zod (de `shared/contracts`) y política CASL.

## 7. Cómo se accede a los datos en `apps/api` (hecho)
- `TenantContext` guarda `{ tenantId, userId }` en un `AsyncLocalStorage`. En HTTP lo fija `TenantScopeInterceptor` con el principal que verificó el guard (§8); en los jobs, quien los ejecute. Rechaza ids que no sean UUID (`InvalidTenantContextError`).
- La transacción usa `DB_TX_TIMEOUT_MS` (10 s) y `DB_TX_MAX_WAIT_MS` (5 s), `DB_LOCK_TIMEOUT_MS` (5 s: cuánto espera una sentencia un bloqueo antes de que la BD la cancele y la petición responda 503) y el pool del rol runtime `DB_POOL_MAX` (10); los cuatro son opcionales y se validan con zod.
- Todo acceso a datos de un tenant pasa por `TenantTransactionRunner.withTenantTransaction(work)`: abre una transacción, fija `app.tenant_id` y `app.user_id` como locales a la transacción, verifica que la BD los confirmó y ejecuta `work`. Sin contexto lanza `MissingTenantContextError` y no consulta nada.
- `DatabaseModule` **no exporta** `PrismaService` (el cliente del rol `app_runtime`, con `omit` de las columnas sensibles de `users`): los repositorios solo reciben el `tx` del runner.
- El cliente de plataforma (rol `app_platform`, ignora RLS) vive en `PlatformDatabaseModule` (`infrastructure/database/platform-*`), que solo importa `modules/platform` y que el worker no tiene. Se usa únicamente mediante `PlatformTransactionRunner.run(tx => …)` y toda fila se escribe con `tenant_id` explícito. `src/architecture.spec.ts` falla si otro módulo importa esos archivos.
- **Tipos de transacción distintos** (`infrastructure/database/transaction-scope.ts`): `TenantTransaction`, `AuthTransaction`, `CrossTenantTransaction` (worker sin tenant) y `PlatformTransaction` son tipos con marca; pasar una de un ámbito donde se espera otro no compila (solo los cuatro runners las crean, con `asScoped`; `architecture.spec.ts` lo vigila). `DatabaseModule.forEntry('api' | 'worker')` entrega a cada proceso solo sus runners.
- `AuthTransactionRunner` (solo para el módulo `auth`) abre transacciones antes de que exista un tenant: anónimas (solo las funciones `auth_*` por correo o hash) o con `app.user_id` (sus propias `refresh_sessions` y `auth_list_memberships`), siempre con `app.tenant_id` vacío.
- Pruebas: unitarias en `src/**/*.spec.ts` (proyecto `unit` de Vitest) y de integración y E2E contra PostgreSQL real en `test/integration/*.test.ts` (proyecto `integration`), con la BD de `packages/db` (`@procesabpm/db/testing`) en una base propia (`procesabpm_api_test`). `pnpm test` en la raíz corre los paquetes de uno en uno.

## 8. Autenticación (`modules/auth`, hecho)
- **Guard global deny-by-default** (`RequestAuthGuard`, el único `APP_GUARD`, §9): toda ruta exige `Authorization: Bearer <access token>` salvo las marcadas con `@Public()` (`common/auth/public.decorator.ts`). Una prueba recorre todas las rutas registradas y falla si aparece una ruta pública nueva que no esté en su lista o una protegida que no responda 401.
- En cada petición el guard verifica la firma del JWT y, en una transacción del tenant, que la cuenta y la membresía sigan `ACTIVE`, que el tenant esté `ACTIVE` (si no, 403 `TENANT_SUSPENDED`) y que la sesión `sid` no esté revocada ni vencida y sea la del tenant `tid`. Una consulta por petición; la caché vendrá después. Luego `TenantScopeInterceptor` ejecuta el handler dentro del `TenantContext` del principal; los handlers leen el principal con `@CurrentPrincipal()`.
- **Flujo:** `POST /auth/login` → lista de organizaciones + token de selección (JWT de 2 min, audiencia propia) → `POST /auth/select-tenant` (con ese token) → access token (JWT HS256 de 15 min, claims `sub`, `tid`, `sid`) + refresh token opaco en cookie `__Secure-refresh_token` (httpOnly, Secure, SameSite=Lax, Path=/auth, 14 días absolutos) → `POST /auth/refresh` (rotación obligatoria con bloqueo de fila; un token rotado que vuelve después de 10 s revoca todas las sesiones) → `POST /auth/logout`. Recuperación: `POST /auth/password-reset/request` (siempre 202) y `/confirm`; invitaciones: `POST /auth/invitations/accept`. `GET /auth/me` devuelve el perfil y la membresía actual; `PATCH /auth/me` edita el propio nombre, idioma y zona horaria (auditado como `account.profile_updated`), y la firma manuscrita para los PDF va en `GET/PUT/DELETE /auth/me/signature` (se enlaza una imagen propia PNG o JPEG, lo único que los PDF pueden dibujar, ya subida y confirmada con la subida en dos fases; `membership.signatureFileId`). La firma en uso no cuenta en la cuota de lo subido sin adjuntar.
- **Intentos y tokens de un solo uso:** el intento de login se reclama de forma atómica en la BD antes de verificar la contraseña (`auth_claim_login_attempt`); el token de selección y el reto MFA llevan `jti` y se consumen una vez; un cambio de contraseña (`POST /auth/password`, reinicio, invitación) anula los tokens emitidos antes (`users.password_changed_at`) y revoca las demás sesiones. El worker olvida los `jti` vencidos cada hora (`AuthMaintenanceModule`).
- **MFA (TOTP, RFC 6238):** `POST /auth/login` responde con `step`: `SELECT_ORGANIZATION`, `MFA_REQUIRED` o `MFA_ENROLLMENT_REQUIRED`; el token de selección solo se emite después del segundo factor. Rutas: `POST /auth/login/mfa`, `…/mfa/enrollment` y `…/enrollment/confirm` (con el token de reto, 5 min, un uso) y, con sesión, `GET /auth/mfa`, `POST /auth/mfa/enrollment[/confirm]`, `/disable` (contraseña + código), `/backup-codes`. SHA-1, 6 dígitos, 30 s, ±1 paso; antirrepetición en la BD; 5 fallos bloquean el factor 15 min (contador en la BD, reclamado antes de verificar); 10 códigos de respaldo de 80 bits guardados como SHA-256. El secreto se cifra con AES-256-GCM (`infrastructure/crypto/aes-gcm-keyring.ts`, llaves `MFA_ENCRYPTION_KEYS`, la primera cifra y todas descifran; se re-cifra al usarse con una llave vieja). Solo el API tiene la llave. La política de la organización (`tenants.mfa_required`, `GET/PUT /settings/security`, permiso `update Setting`) se aplica al ingresar (alta forzada para toda la cuenta), al elegir organización, al renovar y en cada petición (`403 MFA_REQUIRED`); los administradores de plataforma siempre usan MFA.
- **Correos de seguridad** (base-de-datos.md §8.28): `SecurityNotifier` (`application/security-notifier.ts`, sobre `data/security-notice.repository.ts`) encola `email.security_notice` con `enqueue_security_notice`. `notify(tx, …)` va dentro de la transacción del cambio: `ChangePasswordService` (`PASSWORD_CHANGED`), `PasswordResetService.confirm` (`PASSWORD_RESET`, por el `alsoInSameTransaction` de `OneTimeTokenService.consume`), `MfaAccountService` y el alta forzada de `MfaLoginService` (`MFA_ENABLED`, `MFA_DISABLED`, `MFA_BACKUP_CODES_REGENERATED`) y `PlatformSessionService.open` (`PLATFORM_ADMIN_SIGN_IN` con la sesión). `notifyLockout` (transacción propia, mejor esfuerzo) lo usan `LoginService`, `CurrentPasswordVerifier` (`ACCOUNT_LOCKED`) y `MfaFactorVerifier` (`MFA_LOCKED`) cuando el reclamo que bloqueó (`domain/attempt-claim.ts`, número ≥ máximo) tenía la contraseña o el código incorrectos. El worker lo envía con `SecurityNoticeEmailHandler` (`account-email.handlers.ts`, `renderSecurityNoticeEmail`, textos en `i18n/es.ts`): sin token ni enlace con secreto, «si no fuiste tú» lleva a `WebLinks.forgotPassword()` (`/forgot-password`, página que la web debe ofrecer); descarta avisos con más de 7 días en la cola. Siempre activos, sin preferencias; no llegan a cuentas `DISABLED`.
- **Restablecimiento del MFA por soporte** (base-de-datos.md §8.29): quien perdió el dispositivo y los códigos de respaldo vuelve a entrar porque un administrador de plataforma le restablece el segundo factor (§10). No vale para administradores de plataforma (422): su recuperación es un procedimiento del operador. No hay bandera nueva: el siguiente login fuerza el alta si es administrador de plataforma o miembro `ACTIVE` de una organización con `mfa_required` (`MFA_ENROLLMENT_REQUIRED`); si no, el MFA queda apagado. `auth_consume_login_token` rechaza los tokens de selección y de reto emitidos antes de `users.mfa_reset_at`. El correo `MFA_RESET_BY_SUPPORT` va al usuario y `MEMBER_MFA_RESET_BY_SUPPORT` a los dueños de sus organizaciones (`SecurityNoticeEmailHandler` también lo envía: `renderMemberSecurityNoticeEmail`, sin enlace, con el nombre del miembro y de la organización, que lee `worker_member_security_notice_recipient`). Riesgo explícito: quien conozca la contraseña en ese momento inscribe el dispositivo nuevo (confianza en el primer uso); por eso se avisa de inmediato y se exige registrar cómo se verificó la identidad.
- **Avisos que bloquean el inicio de sesión** (base-de-datos.md §8.30): `LoginBlockRegistry` (`modules/announcements/application`, en `LoginBlocksModule`, que importan `auth` y `platform`) guarda en memoria los avisos con `blocksLogin` vigentes o que empiezan en 24 h (`auth_login_blocks()`, una consulta cada 30 s por instancia con tráfico, compartida entre peticiones simultáneas); la política pura (`domain/login-block-policy.ts`) evalúa la ventana con el `Clock` en cada petición, así que el inicio y el fin son exactos sin consultar otra vez. Si falla la consulta, se sigue con la última foto y se registra `announcements.login_blocks_refresh_failed` (falla abierto: sin BD no funciona nada de todos modos); si llegan 200 filas (el tope, con los avisos globales primero) se registra `announcements.login_blocks_truncated`. Respuesta: 503 `MAINTENANCE` con `details {announcementId, title, body, endsAt}` y `Retry-After` hasta el fin (tope 1 día; sin encabezado si no tiene fin); el filtro no lo registra como error. Si aplican varios, gana el que termina más tarde.
  - Aviso `ALL`: `SignInGate` rechaza `POST /auth/login` **después** de la contraseña (devuelve el intento sin fechar `last_login_at`; revela que la contraseña era correcta, como ya lo hace `MFA_REQUIRED`) y `/auth/login/mfa` y `…/enrollment/confirm` **antes** de verificar el código (el reto no se gasta ni cuenta como intento). Los administradores de plataforma nunca se bloquean (son quienes terminan el mantenimiento).
  - Aviso que aplica a una organización (`ALL` o `TENANTS` con ella): `TenantAccessService.verify` lo rechaza **después** de las comprobaciones de membresía y estado, así que un no miembro recibe 401 y no se entera del aviso. Cubre `POST /auth/select-tenant` (antes de consumir el token: se puede elegir otra organización con el mismo), `POST /auth/refresh` (conserva la cookie y la sesión), cada petición con sesión (también la de un administrador de plataforma que es miembro) y el tiempo real (§18). En la lista del login cada organización trae `maintenance: {title, endsAt} | null`, solo para las del propio usuario.
  - No se bloquean las sesiones de plataforma, las visitas de soporte (solo lectura) ni las rutas públicas (salud, recuperación de contraseña, invitaciones).
- **Periodo de eliminación** (§20, base-de-datos.md §8.31): en una organización `PENDING_DELETION`, el dueño o un miembro de un rol admin activo (`hasFullAccess`, `authorization/domain/full-access.ts`) puede volver a elegirla y refrescar su sesión; `TenantAccessService.verify` lo deja pasar solo si quien llama lo pide (`allowDeletionPending`: la selección, el refresh y el guard HTTP; el tiempo real no) y el principal lleva `tenantMode: 'DELETION_PENDING'` (si no, `'ACTIVE'`). `RequestAuthGuard`, entre la autenticación y el permiso, responde 403 `TENANT_PENDING_DELETION` a ese principal en toda ruta que no esté marcada `@AvailableDuringDeletion()` (`common/auth/available-during-deletion.decorator.ts`, solo en el método): hoy `GET /auth/me` (que devuelve `tenantMode` para que la aplicación muestre solo la exportación) y las cuatro rutas de `/data-exports`. La prueba de rutas fija esa lista y exige que todas sean `@AuthenticatedOnly`. Los demás miembros siguen recibiendo 403 al elegirla; el MFA de la organización y los avisos de mantenimiento siguen aplicando; las visitas de soporte y las sesiones de plataforma nunca obtienen este modo.
- **Contraseñas:** Argon2id (19 MiB, t=2, p=1, OWASP), mínimo 10 y máximo 128 caracteres para las nuevas.
- **Contratos:** los esquemas zod de requests y responses están en `packages/shared/src/contracts/auth`; el API los aplica con `ZodValidationPipe` (400 `VALIDATION_FAILED` con las rutas de los campos, sin repetir valores).
- **Trabajo en segundo plano:** `BackgroundTasks` (`common/background`) ejecuta lo que no debe retrasar la respuesta (p. ej. la solicitud de recuperación, para no revelar si la cuenta existe); el apagado espera a que termine.
- **IP del cliente:** `TRUST_PROXY` (`configureHttpApp`, `src/http-app.ts`).
- **Rate limit:** `@RateLimit(policy)` + `RateLimitGuard`, primero por IP y luego por correo (o por token cuando no hay correo), con la interfaz `RateLimiter`; hoy en memoria (`InMemoryRateLimiter`), luego en Redis. 429 `RATE_LIMITED` con `Retry-After`. La IP se agrupa por /64 para IPv6 (`normalizeClientAddress`): un host posee un /64 entero, así que contar la dirección completa sería trivial de rotar. Además de las rutas de auth, llevan límite `/files/uploads`, `/files/:id/confirm` y `/ready`; el guard y el limitador viven en `RateLimitModule` (singleton), para que un módulo compartido con el worker (files) los use sin importar `AuthModule`.
- **Capas:** `http/` (controlador, guard, cookie) → `application/` (un servicio por caso de uso) → `domain/` (política y elegibilidad) y `data/` (repositorios; credenciales solo por funciones `auth_*`).

## 9. Autorización (`modules/authorization`, hecho)
- **Un solo guard global** (`RequestAuthGuard`): primero `AccessTokenGuard` (autenticación) y luego `PermissionGuard`. Nest no garantiza el orden de varios `APP_GUARD` de módulos distintos, así que se encadenan explícitamente: la autorización nunca corre antes de la autenticación ni sin ella.
- **Deny-by-default:** una ruta autenticada que no sea `@Public()` debe declarar `@RequirePermission(acción, sujeto)` o `@RequireAnyPermission([acciones], sujeto)`, o marcarse `@AuthenticatedOnly()` (hoy, entre otras, `GET /auth/me` y las de la propia cuenta: `PATCH /auth/me` y la firma). Si no declara nada, responde 403, aunque el rol sea administrador. Declaraciones que se mezclan (`@Public` con un permiso, `@AuthenticatedOnly` con un permiso, en el método o en la clase) son un **conflicto**: se rechazan con 403 en tiempo de ejecución y detienen el arranque. Una prueba recorre las rutas registradas (`common/auth/route-metadata.ts`) y fija las listas de públicas y de solo autenticadas.
- **Habilidad:** `AbilityService.forPrincipal` carga las reglas del rol de la membresía actual (`role_permissions` + `permissions`, dentro de una transacción del tenant) y construye la habilidad CASL (`@casl/prisma/runtime`, `createPrismaAbility`) para cada petición. El rol sale de la BD en cada petición (se lee junto con las comprobaciones de membresía, tenant y sesión), nunca del JWT: quien cambia de rol o es desactivado pierde el acceso en la siguiente petición. Un rol inactivo no concede nada. `roles.is_admin` no se usa: el administrador lo es por tener `manage all`.
- **Nombres:** las acciones y sujetos son los del catálogo; `manage` y `all` significan lo mismo que en CASL; ninguna acción implica otra (`read` no implica `read_all`). La BD solo guarda reglas `can`.
- **Condiciones** (`role_permissions.conditions`, jsonb): un subconjunto de `where` de Prisma con los campos que el sujeto declara en el `SubjectRegistry` y los operadores `equals`, `in` y `not`. Los marcadores `${user.id}`, `${membership.departmentId}` y `${membership.siteId}` solo valen como valor completo y se resuelven recorriendo el árbol JSON (nunca por reemplazo de texto). Cualquier cosa inesperada invalida **la regla entera**, que se descarta y se registra (`authorization.rule_dropped`): una regla nunca se amplía. Un marcador sin valor (p. ej. un miembro sin departamento) descarta la regla y nunca se vuelve `null`. Un sujeto no registrado no admite condiciones.
- **Acciones con alcance** (p. ej. `read_created` de `Ticket`): sus condiciones viven en el código (`impliedConditions` del sujeto) y se combinan con AND con las guardadas; las guardadas solo pueden restringir, nunca ampliar. El catálogo de acciones con alcance está en código (`CATALOG_SCOPED_ACTIONS`: `read_created`, `read_assigned` y `read_observed` de `Ticket`) y **falla cerrado**: una regla de esas acciones cuyo sujeto no registró su condición se descarta (si no, daría todos los registros). Un auditor lo avisa al arrancar (`authorization.scoped_action_unregistered`) y el registro rechaza registrar un sujeto dos veces. `TicketsModule` registra `Ticket` al iniciar (`onModuleInit`) con sus campos y estas acciones (§14); los tests de autorización usan además un sujeto de prueba (`TestDoc`, en `test/support`).
- **Condiciones de confianza:** `impliedConditions[acción]` también puede ser una **función** `(contexto) => condición | undefined` escrita en código: salta la lista blanca de campos y operadores (puede usar relaciones y `OR`, que las condiciones guardadas no admiten) y devolver `undefined` descarta la regla (falla cerrado). Las guardadas siguen con su plantilla estricta y se combinan con AND. El contexto trae `userId` y `membership.{departmentId, siteId, positionId}` (el cargo sale de la membresía que se lee en cada petición).
- **Acceso por registro** (`domain/record-access.ts`): `ability.can(acción, 'Ticket')` con un nombre es verdadero si existe cualquier regla, aunque sea condicional, así que **no** autoriza un registro concreto. Para eso: `canOnRecord`, `canAnyOnRecord`, `assertCanOnRecord` (lanza 403) y `accessibleWhere` para listados (devuelve `{}` solo para una regla sin condiciones, y un filtro que no coincide con nada cuando no hay regla). El registro debe traer todos los campos a los que se refieren las reglas de su tipo (si falta alguno se deniega: `{ status: { not: 'X' } }` pasaría con un registro cargado sin `status`) y se copia antes de pasarlo a CASL, que escribe en el objeto que recibe. `@CurrentAbility()` entrega la habilidad de la petición al caso de uso.
- **Caché** (`AbilityCache`, interfaz lista para Redis): guarda las reglas sin resolver por (tenant, rol) y por `roles.permissions_version` (5 min de vida y 1000 entradas, LRU). La versión llega en la consulta de membresía de cada petición; si cambió, se recargan las reglas, así que la revocación vale en la siguiente petición en todas las instancias. La habilidad resuelta, que depende del miembro, nunca se cachea. El dueño (`is_owner`) y un rol admin activo reciben `manage all` sin pasar por `role_permissions`.
- **Aprovisionamiento** (`modules/platform`): `TenantRoleProvisioner.createBaseRoles(tenantId, tx?)` crea los cuatro roles de `ROLE_TEMPLATES` con sus permisos; participa en la transacción del alta de tenant (§10).

## 10. Plataforma (`modules/platform`, hecho)
- **Quién:** solo administradores de plataforma (`platform_admins`). Sus rutas llevan `@PlatformAdminOnly()` (excluyente con `@Public`, `@AuthenticatedOnly` y `@RequirePermission`); no construyen habilidad CASL. Una prueba recorre las rutas y fija la lista de las que son de plataforma.
- **Sesión:** `POST /auth/login` (la respuesta indica `platformAdmin`) → `POST /auth/platform/select` con el token de selección → JWT de 15 min con audiencia `procesabpm:platform` y claims `sub`, `sid`, sin refresh. Cada petición llama a `auth_platform_access` (sigue siendo administrador, cuenta `ACTIVE`, sesión vigente con `active_tenant_id NULL`). Un token de tenant en una ruta de plataforma responde 403; uno de plataforma en una ruta de tenant, 401 (la audiencia no coincide). `POST /auth/platform/logout` revoca la sesión.
- **Capas:** `http/platform-tenants.controller.ts` → `application/` (`TenantSignupService` orquesta `TenantRoleProvisioner`, `TenantDefaultsProvisioner` y `TenantOwnerInviter`; `TenantStatusService`) → `data/` (repositorios `tenant`, `tenant-defaults`, `tenant-owner`, `tenant-role`, `platform-audit`) con `PlatformTransactionRunner`.
- **Alta de tenant:** `POST /platform/tenants` (`{slug, name, planCode, countryCode, owner:{email, firstName, lastName}}`), una sola transacción; el orden y lo que crea están en base-de-datos.md §8.16. El slug repetido responde 409 `TENANT_SLUG_TAKEN`; plan o país desconocidos, 422 `INVALID_REFERENCE`. La invitación se encola en el outbox de plataforma como `email.invitation`; el correo lo enviará el worker.
- **Estado:** `POST /platform/tenants/:id/suspend` y `/reactivate`; un tenant suspendido responde 403 `TENANT_SUSPENDED` a sus miembros.
- **Bitácora:** cada acción de plataforma escribe en `platform_audit_logs`.
- **Consola de plataforma (solo API; las pantallas llegan con el frontend).** Todas las rutas son `@PlatformAdminOnly()`: en esta versión hay un solo rol de administrador de plataforma (todos pueden todo; no hay habilidades CASL de plataforma) y la sesión de plataforma ya exige MFA. Cada cambio queda en `platform_audit_logs` con el actor, la IP y los datos (antes/después, motivo). Ninguna ruta devuelve datos de negocio de un tenant: solo agregados.
  - **Primer administrador:** comando de la imagen `migrate` (`seed/create-platform-admin.js`, despliegue.md §4); no hay endpoint público.
  - **Administradores:** `GET/POST /platform/admins`, `DELETE /platform/admins/:userId`. Invitar crea la identidad (o reutiliza la existente, que debe estar `ACTIVE`), la agrega y encola un correo propio (`email.platform_admin_invitation`, enlace de 7 días que no se descarta por esperar en la cola); la MFA se inscribe en el primer login. Revocar cierra sus sesiones de plataforma, nunca deja la plataforma sin un administrador que pueda ingresar, es decir `ACTIVE` y con contraseña elegida (409 `LAST_PLATFORM_ADMIN`; se bloquean todas las filas para que dos revocaciones simultáneas no pasen) y permite renunciar a uno mismo si queda otro.
  - **Tenants:** `GET /platform/tenants` (búsqueda por nombre o slug, filtros `status` y `planCode`, paginado), `GET /platform/tenants/:id` (plan, estado, dueño, empresas, usuarios activos, almacenamiento usado frente a la cuota —misma política que `files`—, tickets de 30 días, última actividad y motivo de la suspensión), `PUT .../plan` (rechaza un plan con menos cupos que usuarios activos), `PUT .../extra-storage`, `POST .../suspend` (motivo obligatorio), `POST .../reactivate` (motivo opcional) y `POST .../owner-invitation` (reenvía la invitación mientras el dueño no la acepte).
  - **Planes:** `GET /platform/plans`, `PUT /platform/plans/:code` (nombre, almacenamiento base y por usuario, % de gracia, máximo de usuarios; sin precios). Los límites rigen al instante porque la cuota se calcula en vivo. La semilla solo **inserta** planes: un despliegue no deshace lo editado aquí.
  - **Anuncios:** `GET/POST /platform/announcements`, `PUT/DELETE /platform/announcements/:id`; los miembros leen los vigentes en `GET /announcements` (`modules/announcements`, `@AuthenticatedOnly`): los de todas las organizaciones y los que nombran la suya. Cada aviso tiene `audience` (`ALL` o `TENANTS` con `tenantIds`, de 1 a 500, sin repetir; una organización inexistente responde 422 `INVALID_REFERENCE`); la consola ve la audiencia y los destinos, los miembros nunca. `GET /announcements/login` (`@Public`, 60/min por IP, `Cache-Control: public, max-age=30`) lista para la pantalla de inicio de sesión solo los avisos **que bloquean el inicio de sesión, para todas las organizaciones y vigentes**, sacados de la misma foto en memoria de `LoginBlockRegistry` (sin consulta por llamada): los dirigidos, las notas de versión y la información para miembros nunca son públicos. Tras cada cambio la consola invalida la caché de bloqueos de su instancia; las demás lo ven en 30 s como mucho. **Bloqueo del inicio de sesión** (`blocksLogin`): ver §8.
  - **Catálogo global:** `GET/POST /platform/catalog/countries`, `GET/POST /platform/catalog/countries/:code/holidays`, `DELETE .../holidays/:date` y `POST .../holidays/regenerate` (reemplaza todos los festivos del año con el calendario por reglas del país, incluidos los agregados a mano; solo países con generador, hoy Colombia).
  - **Operaciones:** `GET /platform/operations/outbox-events/failed?scope=PLATFORM|TENANT` y los reintentos `POST .../platform/:id/retry` y `POST .../tenants/:tenantId/:id/retry` (nunca devuelven el payload; el outbox de plataforma se lee solo con funciones `SECURITY DEFINER`, migración `20261016000000`; reintentar pone los intentos en cero sin riesgo, porque la exclusión entre workers usa la ficha de reclamo `claim_token`, base-de-datos.md §8.26), y `GET /platform/operations/metrics` (tenants por estado, usuarios, almacenamiento total y tickets por día de los últimos 30).
  - **Auditoría:** `GET /platform/audit-logs` con filtros de actor, tenant, acción y fechas.
  - **Cuentas y MFA (soporte):** `GET /platform/users?email=` busca **una** cuenta por su correo exacto (sin prefijos ni búsqueda, para que no sirva para listar cuentas; 404 si no existe) y devuelve id, nombre, estado, si tiene MFA, si es administrador de plataforma y sus membresías, sin secretos (`select` explícito); se audita `user.looked_up` con el id encontrado (o `null`), nunca el correo; 30 por hora por administrador. `POST /platform/users/:userId/mfa-reset` (`{reason 10–500, verification: {method: VIDEO_CALL|CALLBACK_KNOWN_NUMBER|TENANT_ADMIN_REQUEST|IN_PERSON, reference 3–200, tenantAdminUserId}}`, longitudes en puntos de código como en la BD; `tenantAdminUserId` solo y obligatorio con `TENANT_ADMIN_REQUEST`) responde 200 `{resetAt, revokedSessions}`. Todo lo hace `platform_reset_user_mfa` en la transacción de plataforma (base-de-datos.md §8.29): borra el factor y los códigos, revoca todas las sesiones del usuario (de tenant y de plataforma) y cierra sus visitas de soporte, encola los correos al usuario y a los dueños y escribe `user.mfa_reset` en `platform_audit_logs` (motivo, verificación, sesiones revocadas, IP) y `account.mfa_reset_by_support` en el `audit_logs` de cada organización donde es miembro `ACTIVE` (solo el método; quien lo pidió, solo en las organizaciones que administra). Inmediato en v1 (un periodo de espera cancelable es v2). Errores: 400 `VALIDATION_FAILED` (cuerpo inválido, o las comprobaciones 22023 de la función), 404 usuario desconocido, 409 `MFA_NOT_ENABLED`, 422 `INVALID_STATE` (el propio factor, el de otro administrador de plataforma, o quien lo pidió no administra una organización del usuario). Un intento rechazado no queda auditado. 10 por hora por administrador y 3 por día por usuario (en memoria, por instancia, con el `RATE_LIMITER` de `AuthModule`). Capas: `http/platform-users.controller.ts` → `application/platform-user-support.service.ts` → `data/platform-user.repository.ts`.
- **Acceso de soporte (v1, solo lectura).** El tenant abre la puerta: `POST /settings/support-access` (`{hours 1–72, reason}`, por defecto 24 h), `DELETE /settings/support-access` y `GET /settings/support-access` (grant vigente, historial, visitas con el nombre del administrador y cuántas peticiones hizo). Exigen el permiso `manage SupportAccess` (el administrador y el dueño; ningún otro rol lo trae) y una sesión que pasó el segundo factor. Un grant nuevo revoca el anterior en la misma transacción. Desde plataforma, `POST /platform/tenants/:id/support-sessions` abre una visita con la función `platform_open_support_session` (bloquea el grant con `FOR SHARE`): sin grant, 403 `SUPPORT_ACCESS_NOT_GRANTED`. Devuelve un token con **audiencia propia** `procesabpm:support` (claims `sub`=administrador, `tid`, `sid`=visita, `grant`) que vence en el menor de 15 min y el fin del grant; se renueva abriendo otra visita mientras el grant dure; `DELETE .../support-sessions/:sessionId` la cierra.
  - **Aislamiento:** el guard prueba primero el token de soporte; si no lo es, lo trata como token normal (las audiencias no se cruzan: un token normal nunca pasa por soporte, el de soporte no sirve en rutas de plataforma —403— ni de miembro). Solo `GET` y `HEAD` (cualquier otro método: 403 `SUPPORT_ACCESS_READ_ONLY`, después de verificar la visita para que el intento quede atribuido). En cada petición `auth_verify_support_session` comprueba que la visita siga abierta, el grant vigente (sin revocar ni vencido), el administrador siga siéndolo y el tenant exista; si no, cierra la visita y responde 401. La visita vive mientras viva la **sesión de plataforma** desde la que se abrió (`platform_session_id`): cerrar sesión o restablecer la contraseña del administrador la termina en la siguiente petición, sin esperar los 15 min del token. El principal no es miembro: `isOwner` falso, sin rol y con la habilidad fija `SUPPORT_READ_ONLY_RULES` (derivada del catálogo: solo `read` y `read_all`, sin `read_created/assigned/observed`, sin `Webhook`, `AuditLog`, `Setting` ni `SupportAccess`); nunca viene de un rol del tenant.
  - **Auditoría:** cada petición de una visita (método, ruta normalizada sin consulta, resultado e ids de la ruta) se escribe en el `audit_logs` del tenant (`support.request`) con `actor_id` vacío, `support_actor_id` y `support_grant_id`; falla cerrado (la respuesta sale después de escribir la fila). Lo que rechazan los guards también queda (`outcome: DENIED`): un intento de escritura o la lectura de un sujeto oculto, que son justo lo que el tenant quiere ver (`SupportRequestRecorder`). Abrir y cerrar quedan también en `platform_audit_logs`. La descarga de archivos y documentos está permitida y queda auditada por ambas vías.
  - **v2 (pendiente):** soporte con rol de administrador (escribir). Las llaves de autoría apuntan a membresías y un administrador de plataforma no es miembro: habrá que decidir cómo se atribuyen sus escrituras.
- **Eliminación de un tenant (30 días).** `POST /platform/tenants/:id/deletion` (`{confirmName, reason}`; el nombre debe coincidir exacto, si no 422) deja el tenant en `PENDING_DELETION` con `purge_after = ahora + 30 días`, revoca todas sus sesiones y grants de soporte, encola el correo al dueño (`email.tenant_deletion_requested`, sin enlace) y lo audita. Los miembros reciben 401 con el token anterior y, al elegirlo de nuevo, 403 `TENANT_PENDING_DELETION` (el login lo sigue listando para poder explicarlo), salvo el dueño y los administradores, que pueden entrar solo para exportar los datos (§8 y §20). La purga espera a una exportación en curso (como mucho un arriendo de 30 min) y su barrido del prefijo `tenants/<id>/` borra también el zip. `DELETE /platform/tenants/:id/deletion` cancela dentro del plazo y deja el tenant `SUSPENDED` (reactivar es otro paso); vencido el plazo o iniciada la purga, 422.
  - **Purga (worker, `modules/tenant-purge`):** cada 5 min reclama con `claim_due_tenant_purges` (arrendamiento de 30 min, ficha de intento, `SKIP LOCKED`, hasta 3 tenants) y por cada uno: (a) borra por lotes de 1000 todo `tenants/<id>/` (ListObjectsV2 + DeleteObjects) hasta que no quede nada, con un presupuesto de 20 min por corrida; (b) `finish_tenant_purge` borra los datos (`purge_tenant`) y deja la fila como lápida `PURGED` en una sola transacción, y audita `tenant.purged`. Los pasos son idempotentes y reanudables: la lápida es la marca de «hecho»; un fallo libera el reclamo con reintento exponencial (5 min … 6 h) y `purge_last_error`; `PURGED` nunca se vuelve a procesar. Después de la lápida se hace un último barrido del prefijo (un objeto de un trabajo que ya estaba en vuelo al bloquear el tenant). Mientras un tenant está pendiente, los reclamos del worker (`claim_outbox_events`, SLA, esperas y reparto aleatorio) lo saltan: nada trabaja en su nombre. Los efectos externos (S3) nunca van dentro de una transacción de BD. **Antes de purgar el dueño puede pedir una exportación, pendiente del módulo de exportaciones (pendientes.md).**

## 11. Organización y catálogo (`modules/organization`, `modules/catalog`, hecho)
- **Forma común de cada recurso:** `GET /x` (paginado: `page`, `pageSize` ≤ 100, `search`, `includeInactive`), `GET /x/:id`, `POST /x`, `PATCH /x/:id`, `POST /x/:id/activate` y `POST /x/:id/deactivate`. Los contratos zod están en `packages/shared/src/contracts/{organization,catalog}` y la paginación en `contracts/common.ts` (`pageQuerySchema`, `Page<T>`).
- **Permisos:** listar y ver → `read`; crear → `create`; editar y activar → `update`; **desactivar → `delete`** (no hay borrado físico de configuración que se usa: desactivar es el "borrar"). Los calendarios no tienen `is_active`, así que tienen `DELETE /calendars/:id` (la BD rechaza borrar uno usado por una empresa y el calendario por defecto no se borra).
- **Aislamiento:** toda consulta lleva `tenantId` además de la RLS. Un id de otro tenant responde **404 `NOT_FOUND`** (`NotFoundError`), igual que uno inexistente, nunca 403. Una referencia en el cuerpo a un registro de otro tenant (padre de una sede, calendario de una empresa, categoría de una subcategoría, listas de visibilidad) la rechazan las FK compuestas con 422 `INVALID_REFERENCE`.
- **Empresas:** moneda y zona horaria se derivan del país si no se envían (y se vuelven a derivar al cambiar el país sin enviarlas). `POST /companies/:id/make-default` pasa la marca por defecto en una transacción (limpia la anterior y luego fija la nueva, por el índice único); la empresa por defecto no se desactiva ni una inactiva pasa a ser la por defecto (422).
- **Departamentos y cargos:** nombre único por tenant (409). Comparten `NamedRecordsService` / `NamedRecordRepository`.
- **Sedes:** `GET/PUT/DELETE /site-levels/:n` nombran los niveles 1..N sin huecos (solo se borra el último y sin sedes en él). Una sede hija queda un nivel debajo de su padre. `POST /sites/:id/move {parentId|null}` valida en el dominio (`domain/site-tree.ts`) que no haya ciclos (ni consigo misma ni bajo un descendiente) y recalcula el nivel de todo el subárbol. `GET /sites/tree` devuelve el árbol anidado (las sedes cuyo padre está inactivo y oculto aparecen en la raíz).
- **Calendarios:** `PUT /calendars/:id/working-hours/:weekday` reemplaza las franjas de un día en una operación (el solape lo rechaza la exclusión de la BD: 23P01 → `OverlapError` → 409); festivos: agregar (fecha repetida → 409), quitar, listar por año e importar los del país del calendario para un año (`ON CONFLICT DO NOTHING`, devuelve cuántos agregó). `POST /calendars/:id/preview {start, amount, unit, timeZone?}` calcula el vencimiento con `calculateDueDate` y los minutos hábiles con `businessMinutesBetween` de `shared`; la zona horaria por defecto es la del país del calendario y luego la del tenant.
- **Catálogo:** prioridades (orden y color), categorías con visibilidad por empresa y departamento (`PUT /categories/:id/visibility` reemplaza ambas listas; lista vacía = visible para todos en ese eje) y subcategorías (la categoría no cambia después de crearla; `GET /subcategories?categoryId=` lista por categoría).
- **`GET /catalog/available`** (permiso `create` o `create_for_others` sobre `Ticket`): categorías y subcategorías activas visibles para las empresas del usuario (o la que se pida con `?companyId=`, que debe ser una suya) y su departamento. Quien no tiene departamento no ve las categorías restringidas por departamento. Aún no filtra por iniciadores (va con los flujos).

- **Delegaciones** (`/delegations`, `@AuthenticatedOnly`): cualquier miembro crea y cancela las propias; `manage Delegation` extiende a las ajenas (sin él, 404). Solapes y circulares: 409.
- **`ApproverResolver`** (`modules/approvals`, exportado para el motor): `domain/resolve-approver.ts` es una función pura sobre un `ApprovalSnapshot` (probada con tablas de casos) y `ApproverSnapshotRepository` lo carga en 3 consultas sin importar el nivel. `resolveIn(tx, …)` lanza `ApproverNotFoundError`; `diagnose` (`GET /approvals/resolve`, permiso `read ApprovalGroup`) siempre responde con la traza. Las reglas están en pendientes.md.

## 13. Constructor de flujos, backend (`modules/workflows`, `packages/shared/src/workflow`, hecho)
- **`packages/shared/workflow`** (reutilizable por el frontend): `WorkflowVersionDocument` (bloques con sus candidatos, iniciadores, SLA por empresa, firmantes y archivos; transiciones; campos; topes de monto), esquemas zod del `config` de cada tipo de bloque, de la `condition` de las transiciones (operadores de `engine/conditions`) y del `config`/`dataSource` de cada tipo de campo, `validateWorkflowGraph(doc)` y `remapVersionDocument`. Los ids son opacos: un UUID o `new:<nombre>` para lo que el lienzo acaba de dibujar, así que el validador corre sobre un lienzo sin guardar. El `config` nunca lleva ids de bloques, campos ni transiciones (solo códigos de campo e ids de registros del flujo o del tenant), de modo que copiar una versión es copiar JSON.
- **El validador** (puro y determinista; errores bloquean la publicación, advertencias no) revisa: estructura (START y END, alcanzabilidad, bloques sin salida, nombres únicos), salidas por tipo de bloque (DEFAULT en los automáticos, DECISION en los de personas, CONDITION con su DEFAULT), espejo de las reglas de la BD (matriz de `validate_transition`, etiquetas y DEFAULT únicos), asignación (modo y lo que cada modo necesita), plazos CUTOFF, bucles (sin `max_loops` = advertencia; solo bloques automáticos = error), campos (códigos únicos, dónde viven, `config`, `dataSource`, fórmulas), condiciones (campo existente y **dominador** del bloque: disponible; solo en algunos caminos: advertencia; si no, error; operador compatible con el tipo) y topes de monto (campo numérico, columnas de TABLE, bloque propio y de aprobación extra dentro de la versión). El detalle de códigos está en `rules/`.
- **API** (permisos `read` / `update` / `publish` sobre `Workflow`; crear flujos, borradores, observadores y cortes es `update`): `GET/POST/PATCH /workflows`, `POST /workflows/:id/versions` (vacío o copia de `fromVersionId`), `GET .../versions/:vid` (documento completo + validación si es borrador), `DELETE` del borrador, **`PUT .../versions/:vid/graph`** (guardar el lienzo), `GET .../validation`, `POST .../publish`, edición granular (`fields`, `amount-rules`, `steps/:id/{candidates,initiators,signers,sla-overrides,files}`) y `observers` / `cutoffs` del flujo. Un flujo nuevo nace con un borrador START → END.
- **Guardar el grafo:** una transacción; los bloques conservan su id (los campos y listas cuelgan de ellos): los del request se actualizan o crean y los que faltan se borran; las transiciones se borran y se vuelven a crear (con sus ids), lo que libera las reglas de cambio de tipo y de unicidad. Lo que ya impone la BD (reglas de transición, CHECK, FK de otro tenant) no se duplica: su error cancela todo el guardado. Un grafo con problemas **se guarda** (el lienzo es trabajo en curso); solo publicar exige uno válido.
- **Publicar:** una transacción que bloquea el flujo y luego la versión (siempre en ese orden): valida (errores → 422 `WORKFLOW_NOT_PUBLISHABLE` con la lista, sin escribir nada), archiva la publicada y publica el borrador. Dos publicaciones simultáneas: la segunda encuentra una publicada (409).
- **Edición y publicación a la vez:** toda edición de un borrador toma `FOR SHARE` sobre la fila de la versión (o `FOR UPDATE` al guardar el grafo o borrar el borrador) y comprueba que sea `DRAFT` (409 si no). Sin eso, un trigger que leyó `DRAFT` antes de que otra transacción publicara podría confirmar después y cambiar una versión publicada. Una prueba lo comprueba con dos conexiones.
- **Revisión y bloqueo de la versión:** todo lo que escribe una versión (edición granular, guardado del lienzo, publicación, borrado del borrador) toma **`FOR UPDATE`** sobre `workflow_versions` primero. Los triggers de inmutabilidad leen la fila `FOR SHARE`: una transacción que tuviera SHARE y luego actualizara la fila (subir la revisión) se bloquearía con otra igual (dos titulares de SHARE pidiendo la mejora), así que ya no existe el modo SHARE. Cada edición granular incrementa `revision` y la devuelve en el encabezado `Workflow-Revision`; `PUT .../graph` **exige** `revision` (409 `STALE_REVISION` si el lienzo se leyó antes de cualquier cambio).
- **Copiar una versión:** `remapVersionDocument` da ids nuevos (de `uuidv7()` de la BD) a pasos, transiciones, campos, topes y filas hijas, y reescribe las referencias; se copian pasos, transiciones, campos, topes de monto, candidatos, iniciadores, SLA por empresa, firmantes y archivos. No se copian: el estado de ejecución (`step_runtime_states`) ni lo que cuelga del flujo o del tenant (observadores, cortes, documentos, exportaciones, formatos PDF, webhooks, calculadoras).

Los resúmenes `before`/`after` pasan por `sanitizeAuditSummary` (descarta llaves que parecen secretos, corta textos, limita profundidad y tamaño). Las acciones son una lista cerrada (`domain/audit-actions.ts`). `created_at` lo fija la BD al insertar (trigger `audit_logs_database_clock`, base-de-datos.md §8.21).
- Cada ruta que escribe declara `@Audited('accion', …)` o `@NotAudited('motivo')` (`common/audit`); una prueba de rutas exige la declaración en toda ruta no-GET de los sujetos `Membership`, `Role`, `Group`, `ApprovalGroup`, `Workflow` y `Setting`, y un interceptor **solo de las pruebas E2E** falla la petición que responda 2xx sin haber registrado cada acción declarada.
- Cubierto: miembros, roles y permisos, grupos, grupos de aprobación y sus tipos, creación/edición/publicación de flujos, calculadoras, política de seguridad, eventos de cuenta (contraseña, MFA; el restablecimiento del MFA por soporte, `account.mfa_reset_by_support`, lo escribe la propia BD con `actor_id` vacío), emisión de URLs de descarga de archivos y plantillas PDF, y exportación de reportes. Los eventos de cuenta se escriben en el tenant de la sesión, en una transacción propia posterior (el cambio corre sin tenant). Las ediciones de borrador no se auditan (la versión publicada es el registro inmutable).
- **Retención (`modules/retention`, solo el worker; `WorkerModule` lo importa y una prueba de arquitectura impide que lo haga el API):** `RetentionScheduler` revisa cada hora (la primera vez 10 min después de arrancar) y solo entre las 06:00 y las 10:59 UTC (01:00–05:59 en Colombia) llama a `RetentionJob`. El job pide la corrida a la BD (`retention_start_run`: una cada 20 h entre todas las réplicas; si otra ya corrió, no hace nada) y recorre los pasos de `domain/retention-step.ts` en orden (outbox de tenants y de plataforma, notificaciones, sesiones, tokens, auditoría, visitas de soporte, grants, auditoría de plataforma y, al final, las exportaciones de datos vencidas, §20): cada paso llama a su función `retention_purge_*` en lotes de 5000 (el de exportaciones, `retention_expire_tenant_exports` en lotes de 100, y borra cada zip del almacenamiento después del commit), **una transacción por lote** (`WorkerTransactionRunner.withoutTenant`, 60 s de tope), hasta que un lote vuelve incompleto, o hasta 200 lotes o 3 min por paso (lo demás queda para la noche siguiente). Un paso que falla se registra (`retention.step_failed` con el paso, las filas ya borradas, el SQLSTATE y el tipo de error, nunca el mensaje) y la corrida sigue con el siguiente. Al final `retention_finish_run` deja los conteos en `platform_audit_logs` (`retention.run_finished`) y el registro lleva `retention.step_done {step, rows, ms}` y `retention.run_done`: **solo conteos**. Si otra réplica ya corrió, registra `retention.run_skipped` con la hora de inicio de esa corrida. **Apagado:** `beforeApplicationShutdown` aborta una señal (`AbortSignal`) que el job revisa entre lotes y entre pasos: el lote en curso termina (≤ 60 s), la corrida se registra con `interrupted: true` y el worker sale dentro de su periodo de gracia; lo que faltó queda para la noche siguiente. Las ventanas no están en el código del worker: están fijas en el SQL.
- `GET /platform/audit-logs` (consola de plataforma) devuelve `actorUserId: null` en las filas `retention.*`.
- `GET /audit-logs` (`AuditModule`, solo API): filtros `from`/`to` (máx. 366 días, 30 por defecto), `actorId`, `action` (exacta o prefijo `role.`), `subjectType`, `subjectId`, paginación por cursor (`id` UUIDv7, del más nuevo al más viejo). Permiso `read AuditLog`: solo el rol administrador.

## 18. Tiempo real (`modules/realtime`, `infrastructure/realtime`, `packages/shared/src/contracts/realtime`, hecho)
Pasarela Socket.IO en el API (solo WebSocket, ruta `/realtime`, sin sesiones pegajosas) y reparto entre instancias con `LISTEN`/`NOTIFY` de PostgreSQL, sin Redis. Diseño del arquitecto (Opus); detalle de decisiones en `pendientes.md`.
- **Señales (solo ids, nunca datos):** canal `procesabpm_realtime`, JSON `{v:1,k,…}` con `notifications {t,u[]}`, `ticket {t,id,e}`, `document {t,id,d}`, `access {t?,u?,r?,s?}` y `ping`. Una señal es una **pista**: quien la recibe vuelve a comprobar todo con la sesión de cada destinatario; una señal falsa solo provoca una revisión. El **worker** las emite con `pg_notify` **después del commit** (`PostCommitEffects` del despachador del outbox → `RealtimeSignalPublisher`); los disparadores `realtime_*` de la BD emiten las `access` (revocación de sesión, cambio de membresía, rol, tenant o cuenta; ver base-de-datos.md §8.25).
- **Escucha:** `PgSignalListener` abre una conexión propia por instancia (`REALTIME_DATABASE_URL` o `DATABASE_URL`), con un ping a sí misma cada 30 s (detecta un pooler en modo transacción) y reconexión con espera creciente; tras reconectar avisa `sync.required` a los sockets locales.
- **Apretón de manos** (`SocketHandshake`): el token solo viaja en el `auth` del handshake (si aparece en la URL o en `Authorization`, se rechaza sin registrarlo); `Origin` exacto de `REALTIME_ALLOWED_ORIGINS` (sin `Origin`, se rechaza); antes del upgrade, por dirección de cliente (la misma de `TRUST_PROXY`): 50 conexiones sin autenticar, 1 000 abiertas y 600 nuevas por minuto (una conexión que no manda CONNECT se cierra a los 5 s); 600 apretones/min por IP (oficinas detrás de un NAT) y 30/min por usuario; autenticación con `AccessTokenAuthenticator`, el **mismo** código que el guard HTTP (firma, audiencia, membresía, tenant, sesión viva, política de MFA). Un token de plataforma o de soporte no sirve. Los errores de conexión llevan solo `{code}`.
- **Sesión del socket:** `SessionGate` es la única puerta antes de cualquier envío y suscripción (revalida la sesión con memoria de 1 s; un cambio de rol, dueño o ubicación desconecta con `PERMISSIONS_CHANGED`). El token vence en el socket como en HTTP: `auth.required` y 10 s (`REALTIME_AUTH_GRACE_MS`) para mandar `auth.refresh` con el token nuevo (mismo usuario y tenant). `SocketRevalidator` revisa cada 60 s (repartido en ticks de 5 s) y al recibir señales `access`.
- **Tickets:** se suscribe con `ticket.subscribe` (ack con un resumen: estado, paso, vuelta, ids de asignados y último `seq`; nunca título, campos, comentarios ni nombres). Un ticket ilegible, de otro tenant o inexistente responde igual (`NOT_FOUND`). `TicketVisibility` lee con la habilidad CASL **del destinatario** dentro de su transacción de tenant (el mismo filtro que `GET /tickets/:id`). Si pierde el acceso: `ticket.access_lost` en la siguiente señal o en el barrido.
- **Enrutador (`SignalRouter`):** cola acotada (descarta lo más viejo y avisa `sync.required`), agrupa 250 ms, no hace trabajo de BD si no hay un socket local interesado, y autoriza **por destinatario** antes de cada envío. Vacía la cola de a un lote a la vez (lo que llega mientras tanto espera en la cola acotada) y vuelve a comprobar que la sesión siga activa e igual justo antes de enviar. Todo trabajo de BD pasa por `DbWorkLimiter` (4 concurrentes, como mucho 1 000 en espera; el apretón de manos y `auth.refresh` pasan delante del reparto). `RealtimeEmitter` es el único sitio que emite o desconecta (cierra con `SLOW_CONSUMER` si hay más de 100 paquetes pendientes).
- **Límites:** 5 000 conexiones por instancia, 10 por usuario (se cierra la más vieja con `REPLACED`), 20 suscripciones por socket, mensajes de 16 KiB, ráfaga de 20 y 5/s, `auth.refresh` 6/min. Cierres: `TOKEN_EXPIRED`, `SESSION_ENDED`, `MFA_REQUIRED`, `TENANT_SUSPENDED`, `MAINTENANCE` (aviso que bloquea la organización; también como código del apretón de manos y del `auth.refresh`), `PERMISSIONS_CHANGED`, `REPLACED`, `SLOW_CONSUMER`, `RATE_LIMITED`, `SERVER_SHUTDOWN`.
- **Garantías:** entrega **a lo sumo una vez** y sin orden. El cliente vuelve a pedir los datos al conectar, con `sync.required` y al recuperar el foco; las señales no son fuente de verdad. Latencia ≈ intervalo de sondeo del worker (2 s) + 250 ms.
- **Pruebas:** unitarias junto al código; BD (`packages/db/test/realtime-access-signals.test.ts`); integración con `socket.io-client` real contra PostgreSQL real (`realtime-listener`, `realtime-gateway`, `realtime-tickets`, `realtime-multi-instance`), incluida la fuga entre tenants con señales falsificadas y dos instancias del API.
## 19. Bloque NOTIFICATION (`modules/notifications`, hecho)
- Al pasar un ticket por un bloque `NOTIFICATION`, el motor encola `block.notification {ticketId, eventId, stepId}` (como `block.document`). `BlockNotificationHandlers` (worker, transaccional) lee la configuración del bloque **de la versión que corre el ticket**, resuelve a las personas (`CREATOR`, `ASSIGNEES`, `OBSERVERS`, `USER`, `POSITION` con miembros activos, `GROUP` activo; cada persona una sola vez), deja solo a quienes **pueden leer el ticket** (`TicketReaderFilter`, igual que los demás avisos) y aplica sus preferencias para el tipo `SYSTEM`.
- Texto: asunto y cuerpo con el mismo lenguaje de variables de los PDF (`TicketTextRenderer` de `documents`, sobre `DesignResolver`): `{{ticket.number}}`, `{{ticket.title}}`, `{{ticket.creatorName}}`, `{{field.CODE|currency}}`, `{{CODE}}` (forma corta de un campo)… Se valida al publicar (`NOTIFICATION_TEXT_INVALID` si no se entiende o nombra un paso inexistente; un campo inexistente solo avisa, `TEMPLATE_UNKNOWN_FIELD`).
- Canales: en la app se escribe una fila `notifications` (tipo `SYSTEM`, título = asunto, cuerpo = texto; clave única por evento y persona); el correo es su propio evento de outbox (`notification.email` con `stepId`), que al enviar vuelve a comprobar lector y preferencias y renderiza el texto con los datos de ese momento. Un tenant suspendido no manda correos. **El asunto del correo de un bloque lo escribe quien diseña el flujo y viaja sin cifrar en las cabeceras y los registros del proveedor de correo: no debe llevar datos sensibles (responsabilidad del diseñador).** Un texto que no se entiende (no debería pasar: se valida al publicar) se envía tal cual y se registra el paso (`notification.text_unparsed`), nunca el texto.

## 20. Exportación de datos de la organización (`modules/data-exports`, `infrastructure/archive`, hecho)
Durante los 30 días de `PENDING_DELETION` el dueño o un administrador puede llevarse los datos. Diseño del arquitecto (Opus); decisiones B11–B16 en `pendientes.md`. Base de datos: base-de-datos.md §8.31.
- **Quién y cuándo:** solo un principal `DELETION_PENDING` (§8) con acceso total (`assertMayExport`, `domain/data-export-policy.ts`): no es un permiso del catálogo, así que ningún rol personalizado puede recibirlo. Nunca una visita de soporte (403) ni una sesión de plataforma (401). Con la organización `ACTIVE`, 422 `INVALID_STATE` (v1: solo en el periodo de eliminación; abrirlo a organizaciones activas es cambiar esa regla).
- **`POST /data-exports`** `{currentPassword, includeFiles = true}` → 202 con la solicitud `PENDING`. Orden: quién pide (sin gastar un intento de contraseña), 5 solicitudes por persona cada 15 min, la contraseña con `CurrentPasswordVerifier` (cuenta como intento de inicio de sesión y suma al bloqueo; la correcta lo limpia), y en una transacción: la organización sigue `PENDING_DELETION` y faltan 6 h o más para la purga (si no, 422 `EXPORT_TOO_LATE`), ninguna en curso (409 `EXPORT_IN_PROGRESS`; dos a la vez: el índice único de la BD deja una y la otra recibe 409), menos de 5 en total (422 `EXPORT_LIMIT_REACHED`), la fila y la auditoría `data_export.requested`.
- **`GET /data-exports`** (las más nuevas primero, hasta 50) y **`GET /data-exports/:id`**: estado, `includeFiles`, fechas, tamaño, sha256, filas por conjunto (`counts`), `errorCode`, `expiresAt`, `downloadCount`.
- **`POST /data-exports/:id/download-url`** `{currentPassword}` → `{url, expiresAt}`. Cualquier miembro con acceso total (no solo quien la pidió) y **con la contraseña otra vez** (`CurrentPasswordVerifier`, cuenta como intento, después del tope de 10 por hora): un token de acceso o una cookie de refresh robados bastan para ver la lista y el estado, pero no para iniciar una exportación ni llevarse el zip. URL firmada de **5 minutos** como máximo y nunca más allá del vencimiento de la exportación, `attachment; filename="<slug>-export-<aaaa-mm-dd>.zip"`, `application/zip`. Solo `READY` y vigente (409 `EXPORT_NOT_READY`; 410 `EXPORT_EXPIRED`; 404 si no existe o es de otra organización); 10 enlaces por persona y hora. Primero se firma la URL y después, en una transacción, se cuenta (`download_count`, `last_downloaded_at`, un solo `UPDATE` con el reloj de la BD) y se audita `data_export.download_url_issued`: emitir el enlace es el acceso, y un fallo al firmar no deja nada registrado; si la exportación vence entre medio, el enlace se descarta y responde 410.
- **Capas:** `http/data-exports.controller.ts` → `application/data-export-requests.service.ts` y `data-export-downloads.service.ts` → `domain/data-export-policy.ts` (reglas puras y constantes) y `data/data-export.repository.ts`. Contratos y errores en `packages/shared` (`contracts/data-exports`, `Export*Error`).
- **Parte 2, el worker (`data-exports-worker.module.ts`, solo en el worker):**
  - **Qué se exporta:** `domain/export-datasets.ts` (`EXPORT_DATASETS`) es la lista explícita de conjuntos, por grupo (organización, personas y permisos, catálogo, flujos, tickets, auditoría), con las columnas que lee cada uno; nunca `SELECT *`. Cada tabla con `tenant_id` está exportada o excluida con su motivo (`EXPORT_EXCLUDED_TABLES`: outbox, notificaciones y preferencias, webhooks y sus entregas, contadores, uso, `tenant_settings`, estado del despachador, exportaciones planas v2, las propias solicitudes y la audiencia de anuncios), y cada columna de lo que se lee también (`EXPORT_EXCLUDED_COLUMNS`). `members` une `memberships` con `users` y solo trae correo, nombres, documento (B14), estado, idioma y zona: nunca hashes, secretos de MFA, contadores ni bloqueos (además el rol del worker no puede leer esas columnas). Ningún hash, token, código de respaldo ni secreto de webhook sale, ni cifrado.
  - **Prueba de cobertura** (`test/integration/data-export-coverage.test.ts`, contra la BD): falla si una tabla con `tenant_id` no está clasificada, si una columna leída no existe o una columna de una tabla leída no está clasificada, si un nombre exportado parece secreto (`password|secret|token|hash|encrypted|mfa_|key|credential|otp|salt|session|signing|private|recovery|nonce`) sin estar en la lista justificada (`tenants.mfa_required`, `dataset_rows.lookup_key`), si una columna de fecha u hora no declara su formato, y si un lector no lee **exactamente** lo declarado: cada campo de la respuesta se resuelve a su tabla y columna con los metadatos del protocolo (`tableID`/`columnID`, contra `pg_attribute`), así que una expresión, un cast o un alias sobre una columna no declarada fallan (hay una prueba negativa con `users.last_login_at`, `failed_logins AS email` y un cast). Otra prueba corre cada lector con RLS desactivado (`app_platform`) junto a otra organización y solo recibe filas de la pedida: el filtro explícito por `tenant_id` funciona solo.
  - **Lectores:** `data/dataset-readers/<grupo>.readers.ts`, una plantilla etiquetada por conjunto (sin SQL armado con texto), por páginas de 1 000 filas en orden de la clave primaria (keyset), cada página en su propia transacción corta `WorkerTransactionRunner.withTenant` (RLS) y con `tenant_id` filtrado explícitamente. Sin casts ni expresiones: los enums, arreglos y decimales llegan como columnas (los decimales se escriben como texto) y las columnas de fecha u hora se formatean en JS según el formato declarado (`yyyy-mm-dd`, `hh:mm:ss`).
  - **El job** (`DataExportScheduler` cada 60 s → `DataExportJob`): reclama una exportación a la vez (`claim_due_tenant_exports`, arriendo de 30 min), latido cada 60 s (`renew_tenant_export_lease`; si responde `false`, o si no se pudo renovar en 25 min, se deja de escribir), borra lo que haya dejado un intento anterior en la clave y escribe el zip **en streaming** (`infrastructure/archive/zip-archive.ts`, puerto `ZipArchive` con adaptador yazl, ZIP64 cuando hace falta) hacia una subida multiparte (`ObjectStorage.openMultipartWrite`: partes de 16 MiB, una en vuelo mientras se llena la siguiente). Memoria acotada sin importar el tamaño de la organización: una página de filas (1 000, escritas de a una), un archivo (≤ 25 MiB) y dos partes (32 MiB). Contenido, en orden: `LEEME.txt` (en español, `i18n/es.ts`) primero; `data/<conjunto>.jsonl` (fechas ISO, números grandes y decimales como texto) y `csv/<conjunto>.csv` para tickets, valores de campos, eventos, miembros y auditoría (B15: UTF-8 con BOM, RFC 4180, fórmulas neutralizadas con `spreadsheet-text.ts`); `files/index.csv` y `files/<id>/<nombre saneado>` (archivos `CONFIRMED`, de a uno con `ObjectStorage.read` hasta 25 MiB; un objeto ausente o más grande queda en `missingFiles` y no hace fallar la exportación) y `files/index.csv`; y **`manifest.json` al final** (versión, organización, fecha, filas escritas por conjunto y por CSV, archivos, `missingFiles`). La organización no está congelada durante la eliminación (un enlace de descarga agrega una fila de auditoría, la retención nocturna borra filas viejas), así que nada se cuenta por adelantado: cada conjunto se lee por páginas consistentes y el manifiesto dice lo que se escribió (una instantánea `REPEATABLE READ` exigiría una transacción abierta durante horas).
  - **Fin:** se renueva el arriendo justo antes de completar la subida y esa renovación **debe** salir bien (si se niega o falla, se aborta y no aparece ningún objeto); `finish_tenant_export` con tamaño, sha256 y conteos (encola el correo en la misma transacción); si devuelve `false`, o si falla después de completar la subida, se borra el objeto. **Fallo:** solo códigos (`EXPORT_TOO_LARGE` y `EXPORT_TIMEOUT` sin reintento; `LEASE_LOST`, `STORAGE_UNAVAILABLE`, `EXPORT_FAILED` a los 5 min; `WORKER_STOPPED` al minuto), `AbortMultipartUpload` siempre en un `finally`, y en los registros solo ids, códigos, nombres de error y SQLSTATE. Presupuesto `DATA_EXPORT_MAX_RUN_MS` (4 h) y tope `DATA_EXPORT_MAX_BYTES` (100 GiB) en la configuración del worker (B16).
  - **Correo `email.data_export_ready`:** payload estricto `{tenantId, exportId, userId}`; el manejador vuelve a leer todo con `worker_data_export_notice` y no envía nada si no hay fila (un evento falsificado por quien tenga el login de `app_platform` no llega a nadie). Texto en español con el vencimiento en la zona de la persona y un enlace a la página `/data-exports` de la aplicación, nunca al objeto.
  - **Vencimiento:** paso `expire_tenant_exports` de la retención nocturna (§17): las exportaciones `READY` vencidas pasan a `EXPIRED` en una transacción, después se borra cada zip del almacenamiento y se marca; un borrado fallido vuelve en la siguiente corrida y un lote con solo fallos termina el paso. La consola de plataforma muestra el estado de la última exportación (`dataExport: {status, errorCode}` en `GET /platform/tenants/:id`).
- **Pruebas:** unitarias de la política, de los dos servicios (orden de las comprobaciones, carrera → 409, tope de enlaces) y del guard; de la parte 2: declaraciones de conjuntos, CSV/JSONL, nombres de archivo (incluido el escape de carpeta), manifiesto, zip (ida y vuelta con yauzl), subida multiparte con un cliente falso, latido, armado del zip y orquestación del job con dobles (latido perdido aborta la subida, fin rechazado borra el objeto, topes de tamaño y tiempo, archivo ausente listado, filas que cambian durante la exportación, renovación que falla antes de completar, fin que falla después), el planificador (una corrida a la vez, apagado), el correo, el paso de retención; BD (`tenant-data-exports.test.ts`); cobertura del esquema (`data-export-coverage.test.ts`); `data-export-worker.e2e.test.ts` (zip real armado por el worker y descargado con la URL firmada desde SeaweedFS: contenido, sin secretos, sin filas de otra organización, filas de auditoría agregadas y borradas mientras corre y aun así `READY`, correo, evento falsificado, vencimiento y purga); integración (`data-exports.e2e.test.ts`: solicitud, contraseña incorrecta contada, en curso, tope, tarde, carrera, descarga real desde SeaweedFS con nombre de archivo, 409/410/404, quién no puede, fuga entre tenants, la purga borra el zip) y `deletion-period-session.e2e.test.ts` (dueño y administrador dentro y confinados, agente fuera, refresh, sin tiempo real).
